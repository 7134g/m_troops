# 一套语音视频聊天的设计方案
以 Centrifugo + LiveKit 为基础去实现的方案

Centrifugo（信令层）：负责所有控制消息的可靠传递，例如上下麦请求、状态通知、举手发言等。它不传输任何音视频数据。
LiveKit（媒体层）：负责 WebRTC 连接、音视频流的发布（Publish）和订阅（Subscribe），以及媒体数据的转发（SFU）。


# 业务流程例子
### 🎤 上麦流程（从听众变为发言人）
当听众想上麦发言时，会经历一个从“信令请求”到“媒体发布”的完整过程。

#### 客户端侧
1. **发起上麦请求**：听众点击“上麦”按钮，客户端通过 HTTP 请求调用业务后端接口，请求加入语音频道。

2. **获取 LiveKit Token**：业务后端验证用户权限后，调用 `LiveKit` 的服务端 API 生成一个短期有效的 `JWT Token`。这个 `Token` 会包含 `roomJoin` 和 `canPublish` 等授权信息，并返回给客户端。

3. **连接 LiveKit 房间**：客户端使用收到的 `Token`，通过 `LiveKit SDK` 连接到指定的房间。连接成功后，会建立一个 `WebSocket` 信令连接，并默认自动建立“订阅者” `PeerConnection`。

4. **发布本地音频轨道**：
   - 客户端调用 `room.localParticipant.setMicrophoneEnabled(true)` 来请求麦克风权限并创建本地音频轨道。
   - `SDK` 会先向 `LiveKit` 服务器发送一个 `AddTrackRequest`，告知服务器其发布意图和轨道元数据。
   - 收到服务器的 `TrackPublishedResponse` 后，客户端会建立“发布者” `PeerConnection`，并添加该音频轨道，随后向服务器发送 `offer`。
   - 服务器响应 `answer` 后，音频流便开始通过 `WebRTC` 传输到 `LiveKit` 的 `SFU`。

#### 服务端侧
1. **接收并处理发布**：`LiveKit` 服务器（SFU）收到客户端的发布请求和媒体流后，会为其分配一个唯一的 `Track SID`，并将其标记为已发布。

2. **通知其他参与者**：服务器会立即通过信令通道，向房间内所有其他参与者发送 `ParticipantUpdate` 事件，告知他们“用户 X 发布了音频轨道”这一变化。

3. **订阅其他参与者**：同时，服务器会自动将这个新发布的音频轨道，添加到房间内所有其他客户端的“订阅者” `PeerConnection` 中，实现媒体流的分发。

#### 信令同步（Centrifugo 的角色）
**状态广播**：业务后端在处理完上麦请求后，会通过 `Centrifugo` 的 HTTP API，向房间对应的群组频道（如 `group:#{groupID}:signal`）发布一条“用户 X 上麦”的信令消息。房间内的其他客户端收到此消息后，即可更新 UI（例如，在用户头像旁显示麦克风图标）。

### 🔇 下麦流程（从发言人变为听众）
下麦流程与上麦类似，但方向相反。

#### 客户端侧
1. **发起下麦请求**：用户点击“下麦”，客户端调用业务后端接口。
2. **停止发布音频**：客户端调用 `room.localParticipant.setMicrophoneEnabled(false)`。这会向 `LiveKit` 服务器发送信令，并停止发送媒体流。
3. **（可选）断开连接**：如果用户是彻底离开语音房间，客户端可以调用 `room.disconnect()` 来断开与 `LiveKit` 的连接。

> ### 重要建议：对于临时性的“下麦”（如静音），官方推荐使用 静音（`Mute`） 而非 取消发布（`Unpublish`）。因为取消发布和重新发布需要完整的 `WebRTC` 协商，首次字节时间性能较差。

#### 服务端侧
1. **接收停止发布**：`LiveKit` 服务器收到客户端停止发布的通知后，会将对应的 `Track` 标记为已静音或已移除。

2. **通知其他参与者**：服务器会再次向房间内所有其他参与者发送 `ParticipantUpdate` 事件，通知他们“用户 X 的音频轨道已静音/移除”。

3. **更新订阅**：其他客户端的 `LiveKit SDK` 会自动处理这一变化，停止播放该用户的音频。

#### 信令同步（`Centrifugo` 的角色）
业务后端同样会通过 `Centrifugo` 向群组频道广播“用户 X 下麦”的信令消息，以便所有客户端同步更新 UI。

### 🎧 听众收听流程
对于房间内的听众而言，整个流程是完全自动的，他们无需进行任何手动操作。

**自动订阅**：当听众加入 `LiveKit` 房间时，`autoSubscribe` 选项默认为 `true`。这意味着服务器会自动将所有已存在的音频轨道，以及未来发布的任何新轨道，都推送到听众的客户端。

**接收音频流**：当有用户上麦时，`LiveKit` 服务器会自动将该用户的音频轨道添加到听众的“订阅者” `PeerConnection` 中，音频数据便开始传输。

**本地播放**：听众客户端的 `LiveKit` SDK 会在 `TrackSubscribed` 回调中接收到音频轨道，应用只需将其附加到音频元素上即可播放。

### 🔇 静音与取消静音（`Mute/Unmute`）
对于需要临时关闭麦克风但保留在语音频道内的场景，应使用静音功能。

**静音（`Mute`）**：

**客户端**：调用 `track.mute()`。这会将本地 `MediaStreamTrack.enabled` 设置为 `false`，并通知 `LiveKit` 服务器。

**服务端**：服务器收到 `LocalTrackMuteRequest` 后，会向其他参与者发送 `TrackMuted` 事件。

**效果**：其他参与者会收到该轨道已静音的通知，并停止接收其媒体数据。这比取消发布更高效，因为它避免了重新协商的开销。

**取消静音（`Unmute`）**：

**客户端**：调用 `track.unmute()`。这会重新启用本地轨道并通知服务器。

**服务端**：服务器会向其他参与者发送 `TrackUnmuted` 事件，媒体流随即恢复。
